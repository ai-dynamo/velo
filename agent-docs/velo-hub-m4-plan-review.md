# M4 plan review: etcd `HubStore` and recovery

Read-only adversarial review of `/tmp/m4-plan.md` §17 against `lib/velo-hub` at `e0a19ea` (worktree `m3-services`) and etcd-client 0.17.0 source. Paths below are under `/home/ryan/repos/velo-worktrees/m3-services/`.

Verdict: the shape (txn on `mod_revision`, tombstone-settled resolve, watch-fed cache with a barrier, Reserved re-entry by digest) is right, and most etcd claims hold. Three things would ship broken as written: the barrier on txns that write nothing, the pinned-entry remove at shutdown after the store's tasks are cancelled, and fencing after a partition. Two more are design gaps rather than bugs: velo-registered clients never learn `recovered`, and the recovery window is the lease TTL. The per-incarnation lease is the plan's most expensive choice and buys nothing the incarnation check in `touch` does not already give; §5 proposes the simpler design.

## Ranked issues

### Critical

**C1. The watch barrier never completes for a txn that writes nothing.** Plan: "every mutating call waits until the watch task has applied its txn's header revision". A txn whose compare fails (stale `remove`, `put` with wrong `expected`, a second `resolve` whose tombstone already exists) writes nothing, so its header revision is etcd's current revision, which advances with writes to *other* prefixes in a shared cluster. The prefix watch only sees this prefix's events, so it reaches that revision only when something in this prefix changes next. Until then the barrier waits out `step_timeout` and the call answers `Indeterminate`.
Where it bites: the heartbeat handles outcomes serially and awaits each remove (`hub/heartbeat.rs:201-203`, `:328-331`; M1 review N2). Every stale remove (a replacement won the race, the registrant answered after eviction) now costs 5 s of heartbeat stall. `unregister_now` on an entry that just expired becomes `Indeterminate` instead of `is_gone()` (`hub/registration.rs:508-531`), then reads `is_current` from the cache and restores the owner with a 503, when the right answer was "gone".
Change: after any txn the barrier must be able to prove "the watch has seen everything up to R". Use `Watcher::request_progress()` (etcd-client 0.17 `rpc/watch.rs:414`; etcd >= 3.4, and >= 3.4.25 / 3.5.8 because older servers could send a progress notify ahead of pending events, etcd issue 15220) after each txn and wait for a watch response with `header.revision >= R`, events or progress. Put the `or_else` branch of `remove`/`put` to use too: a `get` of the instance key there tells `NotFound` from `Stale` without a second round trip. Conformance must cover this: a failed remove returns within a bounded time with the hook state consistent, on a store whose prefix has no other traffic.

**C2. Shutdown cancels the store's tasks before it removes the pinned entry, so the last remove can never pass the barrier.** `stop` cancels `core_cancel` and joins every core task, including the handle from `spawn_liveness_task` (`hub/mod.rs:366`, `:573-585`), then calls `shared.remove_bounded(pinned)` (`hub/mod.rs:608-613`). If the etcd watch and keep-alive run in the liveness task (the plan puts the pinned keep-alive there), the barrier waits 5 s, the remove answers `Indeterminate`, `is_gone()` is false, and `stop` returns `Err("removing the hub's own entry")` though the delete applied. `lifecycle.rs` tests that assert the pinned entry is gone and the stop result is `Ok` would fail under etcd; the same holds for `Unwind::run` if a startup failure follows the pinned put.
Change: the watch, the keep-alive and the lock lease belong to the store (started at `EtcdStore::connect`, stopped on drop or an explicit `close`), not to `spawn_liveness_task`. The barrier must also degrade honestly: once the store is closing, a call whose txn succeeded returns `Ok` and logs that the hook will not run. Update the `spawn_liveness_task` doc ("backends with native leases return `None`") either way.

**C3. "One hub per prefix" is not enforced after a partition; the old hub keeps writing.** The lock key lives on the store's lease. A hub partitioned from etcd for longer than the TTL loses the lease and the key; a second hub starts; the first reconnects, sees `Lost`, reloads and carries on. Both now write the prefix, both answer `authorize` for the same owners, and the plan's reconciliation assumes "entries written by others (none, with the prefix lock)". Extension state lives in hub memory, so split-brain is not visible in etcd.
Change: add `Compare::lease({prefix}/hub, Equal, my_lease_id)` (`rpc/kv.rs:773`; etcd >= 3.3) to every txn: put, remove, resolve, and the pinned put. A failed lock compare is a terminal `Fenced` state the hub cannot leave; the hub stops (the stop path exists, `HubInner::begin_stop`). Treat a keep-alive answer of TTL 0 for the store's own lease the same way. This is cheap (one more compare per txn) and makes the enforcement claim true. Test: two stores on one prefix, revoke the first's lease out of band, assert its next put fails `Fenced` and the hub stops.

### High

**H1. A velo-registered client never learns the hub restarted; services are silently gone.** The plan's recovery signal is `authorize` answering `recovered`, reached through the HTTP heartbeat, extension routes, or service PUTs. A client registered with `HubClient::register` is kept alive by the hub's velo probes (`hub/heartbeat.rs:241-278`): the handler answers `ok: true` while it holds a response (`client.rs:327-329`), the hub touches the Reserved incarnation, and nothing ever presents the credential. The owner stays Reserved for its whole life, discovery works, and its services (R3-5: "owners re-put their services when they re-register") never come back because nothing triggers the re-registration. The plan's 17.2a table does not list the R3-5 input at all.
Change (needs a ruling): `HeartbeatRequest` carries `hub_id: HubId` (`shared.hub_id`, one per process; `RegisterResponse` must carry it too). The client's handler compares it with the hub id it registered under; on mismatch it marks the registration `recovered` and exposes it (`HubClient::recovered() -> watch::Receiver<bool>` or a `register` that the app calls). Whether the client re-registers on its own is a R2-5 question (no background loops); at minimum the app must be able to find out. `register` must also re-put the live `HubServiceRegistration` guards, or R3-5 is false.

**H2. The recovery window is one lease TTL (30 s by default), and the plan does not say so.** Entries live on leases that only `touch` renews; a dead hub touches nothing, so every entry, pinned or not, is gone 30 s after the hub dies. A hub that restarts later recovers nothing, and every client holds a credential that answers 401 on its next authorized call, then `orphaned` (`client.rs:312-329`) until the hub's probes evict... nothing, because there is no entry; the client registers credential-free and succeeds. That is the pre-M4 behavior, not recovery. The restart test as described ("hub A stops, hub B starts") passes only if B starts within the TTL; a slow rollout or a crash-loop misses it.
Change: state the window in the book and the test; separate the two TTLs (registrant liveness vs hub custody) as in §5, or at least make the lease TTL an explicit store setting with a longer default than the heartbeat-driven liveness.

**H3. Lease TTL vs heartbeat cadence can expire a healthy registrant.** Defaults: interval 10 s, max failures 3, probe deadline = interval, step timeout 5 s (`hub/config.rs:77-85`), lease TTL 30 s. A touch happens only on a successful probe; the tick uses `MissedTickBehavior::Skip`. One skipped tick plus one slow probe plus a 5 s touch deadline exceeds 30 s with no renewal, so etcd deletes the entry while the hub still counts the registrant healthy, the watch reports a removal, authority is revoked, and the client must re-register. Also, 1,000 keep-alive round trips per second at 10,000 registrants is the plan's own number for the hot path.
Change: validate `lease_ttl >= 3 * heartbeat_interval + step_timeout` where the store meets the hub config (`HubBuilder::serve`, step 1), or decouple touch from the lease (§5).

**H4. `touch` as specified cannot be "one keep-alive round trip" with etcd-client 0.17.** `LeaseClient::keep_alive(id)` opens a new bidi gRPC stream per call and does a handshake (`rpc/lease.rs:77-105`); `LeaseKeeper` is bound to one lease id and its sender is private (`rpc/lease.rs:506-535`), so one stream cannot multiplex lease ids through the public API (only the `pub-response-field` feature or a raw tonic `LeaseClient` could). Per-incarnation leases therefore mean either a stream per touch or 10,000 open streams per hub. The plan's "measured at 10,000 leases" would measure the wrong thing.
Change: §5, or budget the raw-tonic multiplexer as real work and measure stream count and etcd memory, not only latency.

### Medium

**M1. A lagging but connected watch is invisible to `continuity`, and it turns a successful re-registration into a dropped owner.** `Degraded` is set only on a watch error. With lag, `put`'s txn succeeds, the barrier times out, the call answers `Indeterminate`; `resolve` also waits on the barrier and fails; `fail_unresolved` delivers the prior's removal, forgets the velo peer and reserves the entry (`hub/registration.rs:257-267`). That is the correct fail-closed outcome for an unknown write, but here the store knew the write applied.
Change: a barrier timeout flips continuity to `Degraded` (back to `Live` when the watch catches up), so `begin_registration` refuses with 503 while the store lags instead of dropping owners. Keep the barrier for `resolve`: D1 depends on it (an applied-then-removed write must be in `progress.removed` before `abort_registration`, `hub/authority.rs:487-507`).

**M2. "Applied" must mean "the hook has returned", and the hook must fire only when the cache actually dropped an entry.** The plan's `watch::Sender<i64>` of the last applied revision is correct only if the watch task sends after the hook call, not after the cache update; otherwise `unregister_now` can still return before `begin_revocation` ran (M1 round 3 N1). On reconnect "from the last revision" must be last applied + 1, or the last DELETE is re-delivered and the hook fires twice. Say both in the contract rule. `prev_kv` is not needed: the cache holds the record and its `mod_revision` for every key in the prefix, and etcd fills `prev_kv` by a range at `mod_revision - 1` at send time, which is missing for a watcher far enough behind compaction. Take the incarnation from the cache entry being removed.

**M3. Reserved should not cache digests; `expected` for the recovery put must be the store's current incarnation.** `Reserved(Incarnation)` is also created by `fail_closed_registration` (`hub/authority.rs:512-532`), which has no digests to store, and a cached digest goes stale if a write the hub lost track of lands later (the round 3 row 1 scenario; a replacement is not a removal, so `Reserved` is not cleared). Read `accepted`/`pending` from `store.get(owner)` inside the transaction, under the registration lock (the hub is the only writer), and use `store.current_incarnation(owner)` as `expected`, not the reserved one; a mismatch between the two is itself a reason to refuse. Require `record.epoch.is_some()`: a pinned or bare record is never recoverable. For `authorize`, answer `recovered` to any presented credential on a Reserved owner without hashing: the real check is the register that follows, and the only leak is "this owner is reserved", which 401-vs-404 already leaks. This keeps SHA-256 off the authorize path (37 ns, `hub/authority.rs:30-34`).

**M4. The `accepted` digest resurrects a credential the protocol said was dead.** After a re-registration the old credential "stops working" (R2-2). Recovery accepts either digest, so after a restart the pre-rotation credential works again until the next re-registration. This is inherent: the hub cannot know whether the response that carried the new credential arrived. Safe enough (a leaked old credential was a compromise already; 16 random bytes, constant-time compare), but say it in the book, and make recovery single-use: the recovery put rewrites both digests.

**M5. `Lost -> Live` reconciliation needs a store API the trait does not have.** `install_removal_hook` fails the second time (`HookInstalled`), and the plan re-runs `synchronize_reservations` with "the store's fresh snapshot". Make the rule: the store reports the gap's removals, then flips to `Live`; the hub then calls `list()` (cache-consistent) and re-syncs. With fencing (C3) the only reconciliation is "vanished", which the removals already covered, so this is mostly about `Removed` and `Reserved` cleanup. Also `begin_revocation` needs a `synced` flag for the "record `Removed` only before the first sync" rule (`hub/authority.rs:577-580`).

**M6. Tombstone lifetime vs how late a put can land.** The claim "a put that arrives after fails its tombstone compare" holds only while the tombstone exists. Set a gRPC request deadline on the client (`ConnectOptions::with_timeout`, `client.rs:855`) equal to `step_timeout`, so a dropped put cannot land later than that, and give tombstones a TTL of at least twice it. etcd rounds lease TTLs up to whole seconds and to its minimum (1.5 x election timeout, 2 s on defaults), and reaps expired leases on a 500 ms tick: tests that assume sub-second expiry will not work.

**M7. Grant-before-txn leaks a lease on every failed put, and the put path is three round trips.** Grant, txn, revoke-old (plus revoke-new on a failed compare, which the plan omits). Under the registration lock that is the hub's registration rate: at 2 ms RTT, 150-250 registrations/s; a 10,000-registrant restart storm takes about a minute. Measure it before the book states a number. §5 makes it one txn.

### Low

**L1. `w/{worker_id}` keys are redundant.** `WorkerId` is a function of `InstanceId` (`lib/velo-ext/src/id/identity.rs:50`, `address.rs:241`; the in-memory store relies on it, `store/memory.rs:65-68`). The only conflict is a 64-bit hash collision between two instance ids. The cache can keep the same worker index the in-memory store keeps, and because the hub is the only writer and every call returns after the barrier, that index is exact for conflict checks. Drop the key, its `mod_revision` compare, and its tracking.

**L2. Contract text.** "A pinned record never expires" (`store/mod.rs:311`) becomes "while its hub runs". `spawn_liveness_task` doc (`store/mod.rs:398-401`) contradicts an etcd store that needs a task. `RegistrationRecord::pending` doc (`store/mod.rs:153-158`) says the hub does not read the digests; M4 changes that.

**L3. etcd leader change and restart are benign but worth a sentence.** On a new leader, every lease's expiry is extended by a full TTL (`lessor.Promote`), so entries outlive a leader change by up to one extra TTL. Watches served by a member that goes away end with an error; the store must recreate them from last applied + 1 (etcd-client reconnects unary calls, not streams). An etcd restart resets all lease TTLs to full.

**L4. Hub A's pinned entry outlives A's crash by one TTL and is reserved on B.** B skips pinned entries in the heartbeat (`hub/heartbeat.rs:233`), so it is never probed; discovery serves a dead hub's peer until the lease expires. Acceptable; say it.

## Answers to the five questions

**1. etcd mechanisms.** Incarnation = `mod_revision` of the instance key, equal to the txn header revision on success: correct, monotone per key, per instance. Compares on `mod_revision`/`version == 0`: correct (absent keys compare as 0). Worker key compare: unnecessary (L1). Lease per incarnation and revoking the replaced one: works, but see H3/H4/M7. Resolve's tombstone: correct, atomic by txn serializability; `None` is settled only while the tombstone lives (M6); "applied then removed before resolve" answers `None` like the in-memory store does (`store/conformance.rs:316-317`), and D1's `progress.removed` covers it only because of the barrier. Watch from R+1 with `prev_kv`: start revision correct (same as `lib/velo/src/discovery/etcd/mod.rs:161-190`); `prev_kv` unnecessary and sometimes absent (M2). Compaction -> `Lost` -> reload: correct in outline; the reload diff must dedupe against the watch and the hub needs an API to re-sync (M5). The barrier: load-bearing and correct for txns that wrote, broken for txns that did not (C1), and must be defined as "hook returned" (M2). Prefix lock key: not fencing without a lease compare on every txn (C3). Shared keep-alive stream: not available through etcd-client's public API (H4).

**2. Behaviors the hub relies on.** Preserved with the barrier as fixed: hook has run when `remove`/`resolve`/`put` return; sync reads reflect the call's own write when it returns; a replacement PUT event is not a removal (cache update only); a removal is reported once (given dedupe on reconnect and a hook fired only on an actual cache drop, M2). Broken or missing: `is_gone()` for a remove of an expired entry becomes `Indeterminate` (C1); the pinned remove at stop (C2); `State::Removed` reclaim needs the `synced` flag (M5); `Reserved` for fail-closed owners has no digests (M3); readers other than the caller see the cache update a few ms late (acceptable; the in-memory window is zero; note it in the contract).

**3. Recovery by digest.** Replay: digests are SHA-256 of 16 random bytes; a store dump yields digests, not credentials; safe. Stale pre-rotation credential: accepted by design, inherent, bounded, document it (M4). Pending digest of a registration that never answered: nobody holds that credential; for a first registration the client holds nothing, answers probes not ok, and the eviction path from M1 round 3 frees the owner; for a re-registration the client holds `accepted` and gets back in. Fail-closed owners (503 from `fail_unresolved`) also recover early through `accepted`, since the client keeps its credential on 503 (`client.rs:566-581`) and extensions dropped the owner's state; safe, and better than waiting for expiry. The `recovered` code fits the client: `credential_rejected` matches only `Unauthorized`/`RegisterAgain`/raw 401 (`client.rs:401-408`), `owns_nothing` adds `NotFound` (`client.rs:414-416`), so the credential is kept on every path; an M2 client that does not know the variant gets `ClientError::Unexpected { 409 }` and also keeps it. The gap is that velo-registered clients never reach `authorize` at all (H1).

**4. Missing.** Fencing after partition (C3); lagging watch (M1); barrier on no-write txns (C1); shutdown ordering (C2); TTL vs heartbeat (H3); recovery window (H2); R3-5 services input absent from 17.2a (H1); 17.2a row 4 assumes no other writer, which only fencing makes true; row 2 needs the `synced` flag. Test gaps: see below.

**5. Simpler design.** Yes; §5.

## 5. A materially simpler store

Keep everything about keys, txns, tombstones, the watch and the barrier. Replace the per-incarnation lease with:

- **One custody lease per hub process**, long TTL (minutes; separate setting), kept alive by a store task. Every instance key, the pinned entry and the lock key are written with it. Every txn compares the lock key's lease (C3). A clean stop does not revoke it; the next hub keeps alive every lease id it finds in the loaded records (leases are not bound to a client) and its own, and drops an old one when no record references it. The lock key gets its own short lease that a clean stop does revoke, so a restart is not blocked for a TTL.
- **`touch` is a cache timestamp**, exactly `store/memory.rs:218-234`: look up the incarnation in the cache, `Stale`/`NotFound` otherwise, write `last_seen`. Zero round trips. R7's invariant (a late touch cannot refresh a replacement) is the incarnation check, as it is in memory.
- **A store reaper** issues the conditional delete (`compare mod_revision == inc, delete`) for entries whose `last_seen` is older than the registrant TTL, like `prune_stale`; the watch reports it like any removal.
- **`put` is one txn**, no grant, no revoke.

What it removes: 1,000 keep-alives/s, N gRPC streams, the grant and revoke round trips, the leaked-lease-on-failed-put case, the TTL coupling in H3, and the recovery window in H2 (custody TTL is now the window and is independent of liveness). What it costs: entries of a dead hub survive for the custody TTL (which is the point); a hub partitioned from etcd for longer than the custody TTL loses everything, same as the plan; the pinned entry no longer needs special handling. R7 ("one fresh lease per incarnation") is a recorded ruling; this needs the user's call, but the ruling's stated reason (a late heartbeat must not refresh a replacement) is satisfied by the incarnation check that both designs need anyway.

## Sound as written

- Key layout, JSON records, `mod_revision` as incarnation, `version == 0` for absence.
- Resolve settled by a tombstone in the same txn as the read; put compares the tombstone absent.
- Watch from R+1 over the whole prefix so every txn's revision is observable; `Degraded` on error, `Lost` on compaction, reload and report the gap.
- The barrier as the way to meet the hub's "hook has run on return" dependence (D1/D2, N1), as a `HubStore` contract rule with a conformance check.
- `install_removal_hook` snapshotting the cache under the cache lock, hook read under the same lock at apply time: correct linearization.
- Startup `register_peer` for snapshot entries; `synchronize_reservations` dropping `Removed` at or above the snapshot's incarnation; `begin_revocation` inserting `Removed` only before the first sync.
- `recovered` as a non-rejection the client keeps its credential on; a 409.

## Tests the plan should add

- Barrier on a failed-compare txn returns bounded with no other prefix traffic (C1).
- Stop with the etcd store: pinned entry gone and `Ok` (C2); startup unwind after the pinned put likewise.
- Two stores on one prefix: lease revoked out of band, next put fails `Fenced`, hub stops (C3).
- Velo-registered client learns of the restart and services come back (H1).
- Hub B starting after the lease TTL: documented outcome (nothing to recover, clients re-register credential-free) (H2).
- Healthy registrant survives one skipped tick plus one slow probe (H3).
- Watch lag (gate the watch task): registration answers 503, no owner dropped (M1).
- Reconnect from last applied + 1 reports no removal twice; lease-expiry removal names the cache's incarnation with `prev_kv` absent (M2).
- Recovery of a fail-closed owner through `accepted`; recovery refused for a bare/pinned record; `expected` mismatch refused (M3).
- Late put lands after the tombstone expired: documented limit, with the client deadline making it unreachable (M6).
- Failed put leaves no lease behind (M7), or no lease at all under §5.
- 10,000 registrants: keep-alive stream count and etcd memory, not only touch latency (H4).
