# Frontend ingest cost ledger: what W1 and W2 can and cannot remove

Dated 2026-09-04. This document records the read-only design research for workstreams W1 (shard the frontend ingest drain) and W2 (cut per-record ingest cost) from `velo-response-plane-win-plan.md`. Three investigators mapped the receive path and an adversarial synthesis checked their load-bearing claims against the code. Nothing here is implemented, and nothing here is measured. Every cost below is counted from source (velo, tokio 1.52.3, flume 0.12.0), not profiled. The W0 probe (`ttft-gap-diagnosis.md`, instrumentation addendum) decides which W1 design is built.

## The receive path, one stage at a time

A response record reaches the client through these stages on the frontend. Line numbers are on branch `drain-credit-return` at 692ba9a.

1. Transport admits the frame and pushes it onto the node-global `message_rx` (`lib/velo-ext/src/transport.rs:680`, unbounded flume).
2. One dispatch task decodes the active message and looks up the handler (`lib/velo/src/messenger/server/mod.rs:173-205`). The handler name costs one allocation per message (`messenger/common/messages.rs:404-406`); the `DashMap` lookup already hashes a `&str`.
3. The `_stream_batch` handler is `.ordered()` (`streaming/messenger_mux/mod.rs:504`), so the message enters a per-sender lane (`messenger/server/dispatcher.rs:392-402`, `lanes.rs`). Eight worker processes give eight lanes.
4. The lane task runs `handle_batch` under the peer's `std::sync::Mutex<PeerIngress>` (`streaming/messenger_mux/ingress/mod.rs:322-392`). Per record: one 13-byte header parse and one `body.to_vec()` copy (`:462`), then `IngressSlot::apply_data` and a `try_send` into the slot's C+1 buffer (`ingress/slot.rs:261-272`).
5. The batch tail calls `collect_grants` (`ingress/mod.rs:389-392`, body at `:729-745`), which walks the peer's entire slot table and calls `IngressSlot::reconcile` on every live slot. `reconcile` starts with `frame_tx.len()` (`slot.rs:176-178`), which in flume 0.12 with default features is a `std::sync::Mutex` acquire on the channel, not an atomic load.
6. `reader_pump` (`streaming/control.rs:314-431`) moves each record from the slot buffer to the anchor's bounded(256) channel. Every loop iteration rebuilds a `tokio::time::timeout` and a cancel-token waiter (`:333-337`). When the slot buffer is empty at poll time, the timeout arms a `Sleep`, which is two acquisitions of the runtime-global timer mutex per record (tokio `runtime/time/mod.rs:96-98, 468-474`; the sharded driver is `cfg(tokio_unstable)` and this workspace does not set it).
7. The anchor consumer parks on the bounded channel and wakes per record.

## Findings that change the plan

**A per-batch full walk scales with streaming concurrency.** Stage 5 is the only ingest cost that grows with live slots rather than with record rate. At the tier-3 shape (concurrency 8192 over 8 processes, about 1,024 live slots per peer, which is also the figure `MAX_INGRESS_SLOTS_PER_PEER`'s doc names at `ingress/mod.rs:53-54`) that is about 1,024 mutex acquires per batch, or about 25 per record at 40 records per batch. Neither diagnosis named it. It is a prediction, not a measurement: `velo_streaming_mux_live_slots` and the `velo_streaming_mux_records_per_batch` histogram both exist and W0's frontend scrape will carry them.

**Reordering batches from one peer is not safe, for two reasons the protocol does not advertise.** First, the worker flushes `OpenSlot` in its own batch on purpose (`peer_batcher/mod.rs:527-542`), so a `Data` batch that overtakes it hits `checked_slot` returning `None`, is dropped as `closed_slot`, and the later `IngressSlot::new` sets `next_seq` past the lost record (`ingress/mod.rs:552-555, 704-709`). That is silent head truncation of a response stream, visible today only as a counter. Second, `note_batch_seq` computes the gap with `wrapping_sub` and the metric does `inc_by(f64::from(gap))` (`ingress/mod.rs:427-439`, `observability.rs:704-706`), so one late batch adds about 4.29e9 to `velo_streaming_mux_batch_seq_gaps_total` and rewinds the baseline for the next one. Any W1 design must keep the per-sender lane order. Per-slot `frame_seq` ordering (`slot.rs:121-143, 229-252`) is sufficient for `Data` only once `OpenSlot` has landed.

**W2(c), "one wake per decoded batch", is already met.** flume fires a waker only when a receiver is parked and pops the hook it fires (flume `lib.rs:499-533`), so k records for one slot in one batch already cost one wake. A batch's records belong to distinct slots, hence distinct anchors and consumer tasks, so "one wake across a batch" has no meaning. What costs about two wakes, two park cycles, and two `Arc<Hook>` allocations per record is the two-hop structure (slot buffer to `reader_pump` to anchor channel to consumer). Collapsing that hop is a design change, not a line item: credit is issued against the mux-owned buffer and must never be issued against the anchor channel because it has other writers (`slot.rs:19-23`), and deleting `reader_pump` for mux streams deletes the heartbeat watchdog and `velo_streaming_reader_pump_backpressure_total`, the saturation diagnostic the runbook names.

**W2(b), the per-record copy, is real but deferred.** The copy is at `deliver`'s call site (`ingress/mod.rs:462`), one malloc plus memcpy per record, estimated 35 to 55 ns. Removing it means flipping the element type from `Vec<u8>` to `Bytes` across the slot buffer, the anchor channel, both `reader_pump` halves, and the cached sentinels. `velo-ext`'s `FrameTransport::bind` pins `Vec<u8>` (`lib/velo-ext/src/streaming.rs:110-114`), but the mux path can bypass it with an inherent method because `AnchorManager` already holds the concrete `Arc<MessengerMuxTransport>` (`anchor.rs:848-869`). Do not add a defaulted `bind_bytes` to `velo-ext` for one memcpy: it forces a coordinated `velo-ext` and `velo` release with an `=` pin update. This item rides on the two-hop collapse if that is ever built.

**W2(d), the accept-timeout task leak, is confirmed exactly as described.** `MessengerMuxTransport::bind` spawns one task per attach that sleeps 60 s (`messenger_mux/mod.rs:144, 960-984`) and nothing on the success path cancels it, so at 3,000 attaches per second about 180,000 tasks, timer entries, and cancel-token waiters are live in steady state. `expire_bind` is already idempotent (`ingress/mod.rs:262-264`), so a single reaper task with a monotonic `VecDeque` of deadlines replaces all of them with no cancellation. The reaper must keep the unconditional `core.drains.remove` (`:971-976`, the comment there is the reason) and the "no OpenSlot arrived" warning. This is a memory and task-count fix, not a per-record CPU fix.

**W2(a), the per-frame timeout, is the largest and cheapest per-record win, with one unmeasured premise.** The `Sleep` is armed only when the slot buffer is empty at poll time. `ttft-gap-diagnosis.md` says the per-stream buffers are empty at tier 3, which means the pump parks on nearly every record; that is a diagnosis claim, not a counter. The fix hoists both futures out of the loop and measures the deadline from the last frame, not from a fixed-phase ticker, so detection stays at exactly three heartbeats (a ticker would widen it to between three and four, and silently falsify the "about 15 s" figure in the adapter's doc). A permanent `velo_streaming_reader_pump_deadline_arms_total` counter is the only available cost proof, because no tokio API reports timer registrations.

**The plan's 20 to 40 percent W2 figure summed items that are not independent.** The honest W2 arm is (a) plus (d): two global-timer-mutex round trips and two token-notify operations per record, plus 180k tasks and timers. Do not book (b) or (c).

## W1 candidate designs, ranked, with the decision held for W0

W0 decides between the first two by measuring where the standing backlog sits and what stage 5 costs.

- **W1-B, touched-slot reconcile.** Keep the lane and the mutex. `handle_batch` records the slot indices it delivered into (a scratch `SmallVec` reused across batches) and reconciles only those plus a small round-robin cursor stride, so a drained but untouched slot is still visited within `ceil(slots/stride)` batches. The drain doorbell from `drain-credit-return` and the periodic sweep remain as backstops. Per-batch cost goes from O(live slots) to O(slots touched + stride). Risk: the doorbell becomes load-bearing; the added latency of a deferred visit is `drain_visit_floor / initial_credit` per record (`messenger_mux/mod.rs:323-329`), about 8 microseconds at the 2 ms and 256 defaults, rising linearly as credit falls. Chosen if the lane stage dominates the W0 split and live slots per peer are in the hundreds or more.
- **W1-C, lean lane.** Keep everything and delete fixed per-batch overhead: the handler-name allocation in decode, one of the two boxed futures per lane item (a defaulted synchronous escape hatch on the crate-private `ActiveMessageHandler`, which `_stream_batch` qualifies for because the ingress module never awaits), and three clones in `AmExecutorAdapter` (`handlers/mod.rs:520-532`). About one allocation, one boxed future, and three clones per batch at about 20k batches per second. Chosen if W0 shows the lane wait is not slot-count bound; it composes with W1-B.
- **W1-A, slot-sharded apply behind the per-peer order gate.** The lane task becomes a router that decodes and routes records to N per-(peer, shard) tasks keyed by slot index. It is the only design that adds cores, and it is deferred: its failure modes pass a smoke test and fail at tier 3. A shared `peer_bytes` budget implemented as fetch-add-then-check transiently over-reports and makes `try_reserve_pair` return `Applied::Fault(ProtocolError)` (`slot.rs:234-236`), which kills a healthy stream; and a `RetireEpoch` broadcast not enqueued to every shard ahead of the new epoch's records applies new-epoch records against old-epoch slots. Build it only if W0 shows the stage is core-bound after W1-B and W2.

If W0 shows the `message_rx` wait (the single decode task) dominates, none of the three is the first move; the decode side needs work and the W1 brief will be rewritten. Sharding the decode task is mechanically trivial (flume receivers are MPMC and cloneable) but the teardown sweep at `server/mod.rs:344-360` assumes one drainer and the ordered lane assumes per-sender arrival order, so it needs an elected sweeper and a reorder-tolerant handoff into the lane.

## Env gates and rig arms (spec, not yet wired)

- `DYN_VELO_RESPONSE_INGEST_RECONCILE=full|touched|touched:<k>` with `k` in 1..=64, default `full`. Parsed in the adapter next to `parse_env_range` (`velo_response.rs:329-347`), threaded into `MuxConfig` through `mux_config()` (`:318-326`), refused at mux construction when the stride is zero. A bad value is a hard error, following `VeloTransportKind::parse`, because a mistyped gate that silently defaults makes the matrix measure baseline under a W1 label. Rename if W0 changes the W1 mechanism; a gate named for a mechanism it does not implement is the two-spellings drift the compatibility policy forbids.
- `DYN_VELO_RESPONSE_INGEST_FAST_PATH=0|1`, default `0`. One switch for W2(a) and W2(d). (d) reaches the mux through `MuxConfig`; (a) does not, because `reader_pump` is spawned in the `_anchor_attach` handler from a `PumpContext` built by the `AnchorManager` (`control.rs:587-597`) and serves every transport. (a) therefore needs one new `VeloBuilder` field feeding `AnchorManagerBuilder` (`lib.rs:166-171, 353-360`).
- Both gates are logged at `VeloNode::build`, written into `rig_run_meta.json`, and asserted after each run the way the ucx transit check works (`t3-matrix.sh:254-256`). Without that, a stale wheel makes `velo1` run identical to `velo0` and the matrix reports a false negative.
- Arms `velo1`, `velo2`, `velo12` are added exactly the way `mux18p` was, and every existing arm's case branch, including the defaults, explicitly unsets both gates so a control rep after a variant rep in the same shell cannot inherit them. `summarize.py`'s directory-name fallback must check `velo12` before `velo1`.

## What W0 must read before W1 is written

- `velo_streaming_mux_live_slots` per peer on the frontend at tier 3 (premise of W1-B's payoff).
- The `velo_streaming_mux_records_per_batch` distribution for received batches (denominator of W1-B's payoff and the wake amplification of W1-A).
- The `message_rx` versus lane split from the W0 instrumentation.
- A discriminating rep is cheap: the same request rate at concurrency 2048 instead of 8192 cuts live slots per peer by four. If lane wait per batch falls with it, the full walk dominates.
